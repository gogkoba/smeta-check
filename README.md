# Проверка сметной документации

Пайплайн `документы → parse → normalize → validate → report`: на входе папка с локальными
сметами в xlsx, на выходе протокол замечаний, отсортированный по сумме потенциального
завышения. Ведомости объёмов работ, если лежат рядом, подхватываются сами — по колонке
«№ в ЛСР» объёмы сметы сверяются с ведомостью.

Рабочий прототип на открытых данных: проверяет реальные сметы из ЕИС и считает суммы
влияния. Это ещё не продукт — он снимает часть ручной сверки, а не закрывает работу
сметного отдела целиком.

## Запуск

```
python -m smeta.cli --input data/corpus --out data/reports/protokol.xlsx
python tests/test_pipeline.py    # регрессия
python tools/score.py            # recall на синтетике с заложенными дефектами

python tools/pin_ca.py                              # закрепить корень Минцифры (разово)
python tools/search_eis.py --per-query 2 --limit 48 # найти закупки в ЕИС
python tools/fetch_docs.py --urls data/urls.txt --only-smeta --dest data/corpus
```

## Как устроен парсер

Позиция занимает блок строк, а не одну. Колонки размечаются по строке нумерации
(«1 2 3 4…» под шапкой) — она есть в любой выгрузке и переживает объединённые ячейки;
ею же отрезается зеркальная копия данных, которую ГРАНД-Смета печатает правее таблицы.

Поддержаны обе методики:

- **базисно-индексный** — ОТ / ЭМ / ЗТ / «Итого по расценке» / НР / СП / «Всего по позиции»;
- **ресурсно-индексный (Методика 2020)** — ресурсы с шифрами ФСБЦ-2022, «Итого прямые
  затраты», базисная и текущая цена в соседних колонках, строки расчёта объёма
  («Объём: 1,9*1,5*8+1,2*1,5») — они сохраняются и попадают в протокол.

## Правила проверки

| Правило | Что ловит |
|---|---|
| `arithmetic` | объём × цена × коэффициент по каждой составляющей, затем сумма против итога |
| `position_total` | «Всего по позиции» ≠ расценка + НР + СП |
| `vor_mismatch` | объём в смете не бьётся с ведомостью объёмов работ |
| `duplicate` | одна и та же работа посчитана дважды |
| `price_above_median` | цена за единицу выше медианы по корпусу |
| `overhead_out_of_range` | НР/СП вне норматива по виду работ |
| `overhead_inconsistent` | один вид работ — разные проценты НР/СП внутри сметы |
| `coef_on_materials` | повышающий коэффициент на материальную позицию |
| `market_price` | цена по конъюнктурному анализу — нужны три КП по 421/пр |
| `no_basis` | позиция вообще без обоснования |
| `round_volume` | объёмы 500 / 1000 — прикидка, а не подсчёт |
| `subtotal_mismatch` | итог раздела ≠ сумма позиций |

## Результаты

**Корпус**: 3 объекта из ЕИС (капремонт школы в Омске, Юнкерское училище, капремонт
кровли и фасада), 37 файлов, 27 локальных смет, обе методики расчёта.

- разобрано **27 смет из 27**, из них 19 полностью чисто
- **2320 позиций**, 3124 строки НР/СП, 112 нераспознанных строк (около 4%)
- ведомости объёмов: **2174 строки из 2232** привязаны к позициям смет
- 771 замечание, сумма влияния 654 740 ₽
- время: 12 с на 27 смет

**Синтетический корпус** с заложенными дефектами: 10 из 10 поймано, 2 замечания сверх
плана — оба проверены вручную и верны. **Регрессия**: 9 тестов, все проходят.

## Честные оговорки

**Про синтетику.** 10 из 10 — результат на собственных фикстурах: дефекты закладывал тот
же человек, что писал правила.

**Про нормативы НР/СП.** Таблица в `norms.py` — заглушка; боевые значения в приказах
Минстроя 812/пр и 774/пр. Пока справочник неполный, правило `overhead_out_of_range`
молчит там, где вид работ неизвестен, и помечает свои замечания как требующие сверки.
`overhead_inconsistent` от справочника не зависит — сравнивает смету саму с собой.

**Про источники.** Из 48 закупок сметы в xlsx нашлись только в трёх: остальные публикуют
сметную часть в PDF или в архивах rar. Это само по себе вывод — без ветки PDF корпус не
масштабируется.

## Шесть ложных срабатываний, пойманных на реальных данных

Главный результат работы. Ни одно не было багом кода — все шесть про непонимание того,
что означают колонки:

1. **Коэффициенты по составляющим.** ОЗП=0,8, ЭМ=0,8, МАТ=0 применяются к каждой части
   отдельно, поэтому «объём × общая цена × коэффициент» давало 150 ложных замечаний.
2. **Шифр конъюнктурной цены.** `ТЦ_20.3.03.07_77_7722699172_05.07.2022_01` — это регион,
   ИНН и дата, а не товар: под одним шифром пять разных светильников.
3. **Уровень цен внутри одной колонки.** Для ресурсов вне нормативной базы графа «цена на
   единицу» дана в текущем уровне, а итог — в базисном. 44 позиции выглядели ошибкой.
4. **Номер позиции с пометкой.** «2 О» (оборудование) не разбирался как число, позиция
   приклеивалась к предыдущей и ломала проверку итогов.
5. **Смешение уровней цен в медиане.** Базисная цена из одной сметы и текущая из другой
   отличаются в разы законно — медиана теперь считается отдельно по уровню и единице.
6. **Ссылка «№ в ЛСР» не всегда правда.** В части комплектов ведомость нумерует позиции
   по-своему, и номер указывает на чужую строку — причём наименование совпадает, потому
   что одна и та же работа повторяется для разных помещений. Дало 170 выдуманных
   расхождений на 9,6 млн.

Из последнего родился приём, которым я доволен больше всего: **связка калибруется целиком,
прежде чем ей верить.** По каждой паре «смета — ведомость» считается доля сходящихся
строк; если меньше 70%, сверка не проводится вовсе и пайплайн честно пишет:

```
ведомость 02-01-02: сверка не проводилась — по 29 строкам сошлось только 45%,
нумерация «№ в ЛСР» не совпадает со сметой
```

Сказать «не могу проверить» полезнее, чем выдать сотню расхождений, которые сметчик будет
день опровергать. После калибровки из 170 расхождений осталось 3.

## Доступ к zakupki.gov.ru

Сайт подписан цепочкой Russian Trusted Root CA (Минцифры), которой нет ни в `certifi`,
ни в хранилище Windows. `tools/pin_ca.py` забирает корень из живой цепочки, печатает
отпечаток для сверки с gosuslugi.ru/crt и сохраняет в `data/certs/`. Дальше проверка
строгая, без отключения TLS.
